# Архитектура

## Поток данных

```
Steam GC (бот) ──(свежая история: последние 50 матчей; соли URL)───────────────┐
deadlock-api.com ──(история матчей; .meta из своего хранилища, bzip2; соли URL)──┐
                                                                                ▼
replay<N>.valve.net ──(.meta, zstd; запасной путь по соли)───────────────► syncer ──► Postgres ◄── server (gRPC :9090) ◄── gateway (REST :8080)
```

1. `SyncPlayer` (RPC или периодический тикер по `SYNC_ACCOUNTS`) тянет историю матчей игрока — объединение последней страницы из Steam GC (если настроен бот) и полной истории deadlock-api (`source.MergedHistory`) — и кладёт заголовки в `matches` + `player_matches`. Новые матчи получают `meta_status = 'pending'`.
3. Фоновый `Syncer.RunProfiles` раз в минуту, пока есть работа (иначе раз в 15 минут), берёт до 1000 аккаунтов без профиля Steam или с профилем старше 7 дней (сначала отслеживаемые, потом все из сохранённых матчей) и одним запросом `GET /v1/players/steam?account_ids=…` у deadlock-api получает имена, аватары и, для отслеживаемых, списки друзей.

Кроме того, `ResolveSteamVanity` по запросу пользователя спрашивает `steamcommunity.com/id/<имя>?xml=1` (без ключа API), чтобы превратить ссылку с ником в account id. Это один запрос на поиск, фонового трафика к Steam нет.

2. Фоновый воркер `Syncer.Run` разбирает очередь `pending`: сначала берёт `.meta` из хранилища deadlock-api (`/v1/matches/{id}/metadata/raw?disable_steam=true`), а если там нет — получает соль (сначала у Steam GC, потом у deadlock-api: `source.SaltChain`) и качает файл с CDN Valve; распаковывает, декодирует protobuf и в одной транзакции сохраняет сырой файл и производные таблицы.
3. API только читает из Postgres. Статические данные игры (герои, предметы) встроены в бинарник.
4. Веб-интерфейс (`web/`, Next.js) рендерит страницы на сервере, запрашивая REST-gateway; браузер с Go API напрямую не общается. Локализация ru/en — свой словарь без библиотек (`web/src/i18n`): язык интерфейса и язык имён из игры — независимые настройки в cookies.

Один процесс `cmd/server` держит gRPC-сервер, REST-gateway (ходит в gRPC по loopback) и воркеры синхронизации.

## Правила зависимостей

Проверяются линтером `depguard` (`.golangci.yml`), нарушение ломает `dev check`:

- **pgx и SQL — только в `internal/db`.** Остальным нужен интерфейс, а не пул.
- **gRPC и типы API (`gen/go`) не проникают в ядро**: `meta`, `compress`, `gamedata`, `source`, `syncer` о транспорте не знают.
- **`internal/server` импортирует только `cmd/server`.**

Не проверяются автоматически, но обязательны:

- **Интерфейсы объявляет потребитель.** `server.Store`, `server.PlayerSyncer`, `syncer.Store` описывают ровно то, что нужно пакету; `*db.DB` реализует их неявно. Новый метод БД для сервера → добавить в `db` и в `server.Store`. Благодаря этому `server` и `syncer` тестируются фейками без Postgres.
- **Сборка зависимостей — только в `cmd/`.** Пакеты `internal/` не читают env и не создают друг друга.
- **Зависимости направлены вниз**: `cmd` → `server`/`syncer` → `db`/`source`/`meta` → `pb`/`compress`. Циклов и обратных импортов нет.

## Принятые решения

**`internal/db` возвращает типы API (`v1.Player`, `v1.Match`, …), а не собственные модели.** Сознательное упрощение: API сейчас — почти прямая проекция таблиц, отдельный доменный слой удвоил бы объём кода (структуры по 20+ полей и маппинг) без пользы. Цена: изменение формы ответа API затрагивает SQL-слой. Пересмотреть, когда появится логика, которой нужны данные не в форме API (агрегаты, сравнения игроков), — тогда ввести доменные типы в `db` и маппинг в `server`.

**Сырой `.meta` хранится в БД (`matches.meta_raw`).** Valve удаляет реплеи через некоторое время. Байты — ровно как скачаны: от deadlock-api это bzip2, с CDN Valve — zstd; `internal/compress` различает по magic-байтам.

**429 — не неудача.** Ответ «слишком много запросов» откладывает матч на `Retry-After` (`DeferMeta`), не тратя попытку. 429 хранилища метаданных придерживает всю очередь; 429 солей ставит на паузу только путь через соли (лимит Steam — 3 запроса в час), а матчи из хранилища качаются дальше. `StoreMeta` идемпотентен: удаляет и заново строит производные таблицы матча, поэтому при изменении схемы данные можно пересчитать из `meta_raw` без сети.

**Пересборка производных данных — автоматическая.** У каждого матча `matches.derive_version`; константа `db.DeriveVersion` — версия того, что выводится из `.meta`. При старте `syncer.Run` сначала пересобирает все матчи с версией ниже текущей (`NextStaleMeta` → `MetaRaw` → `RederiveMeta`), только из `meta_raw`, без сети: ~700 матчей за ~20 с. `RederiveMeta` никогда не пишет в `meta_raw`. Битый файл пропускается и логируется, а не блокирует очередь.

**Агрегаты прогресса считает фронт.** `ListPlayerMatchFacts` отдаёт по каждому матчу игрока компактную сводку (история + души к 5/10/15/20 мин, время до 10k/20k/30k, источники душ, уровень лобби), а форма, тренды, сессии и рекорды считаются чистыми функциями в `web/src/lib/progress.ts`. Так новые срезы и фильтры не требуют новых RPC, а логика покрыта быстрыми юнит-тестами. Сводка ~1200 матчей — около 0,5 МБ JSON между контейнерами; когда станет много пользователей или истории, агрегировать на сервере.

**Провайдеры за интерфейсами.** Соль URL и история матчей приходят через `source.SaltProvider` / `source.HistoryProvider`. Реализаций две: `steamgc.Bot` — собственный клиент Game Coordinator Deadlock от имени отдельного аккаунта-бота (`STEAM_BOT_USER`/`STEAM_BOT_TOKEN`, вход — `go run ./tools/steambot login`), и `source.DeadlockAPI`. Бот первичен: он видит матч сразу после окончания, у deadlock-api история приходит с задержкой в часы и дни (если аккаунт не в друзьях у их ботов). deadlock-api остаётся источником полной истории (GC отдаёт только последнюю страницу) и запасным путём, когда бота нет или GC недоступен. Бот держит одну GC-сессию, сам переподключается (1 мин → 30 мин), делает не больше одного запроса к GC за раз и не чаще раза в 3 с. Ответы GC «занят / лимит / матч ещё идёт» превращаются в `RateLimitError` — syncer откладывает матчи, не сжигая попытки. GC показывает историю только себе и друзьям, поэтому бот должен быть в друзьях у отслеживаемых аккаунтов.

**Steam GC — через `paralin/go-steam` + `paralin/go-deadlock`.** Готовые и живые библиотеки (новая авторизация Steam с refresh-токеном и Steam Guard, TCP-соединение с CM, сгенерированный API GC). Они тянут свои зависимости (logrus, `aperturerobotics/protobuf-go-lite`), поэтому импортируются только в `internal/steamgc`; наружу пакет отдаёт типы `source`. Логи go-deadlock приглушены, ошибки приходят событиями и возвратами.

**Собственный раннер миграций** (`db.Migrate`): файлы `NNNN_name.sql`, каждая в своей транзакции, advisory lock от гонок при одновременном старте, применяются при старте сервера. Только вперёд, без down-миграций.

**Ручной SQL, без ORM и билдеров.** Массовая вставка — через `CopyFrom`.

**Минимум зависимостей.** В `go.mod` только pgx, grpc, grpc-gateway, protobuf. zstd скопирован из stdlib; VPK, KV3 и ресурсы Source 2 разбираются собственным кодом.

**Снимок данных игры встроен в бинарник** (`go:embed`), серверу не нужна установленная игра. `item_id` в метаданных матча — это `MurmurHash2(lower(ключ), 0x31415926)`.

**Иконки не в git и не в Go-сервере.** Это арт Valve: он извлекается из локальной установки игры в `data/icons` (игнорируется git) и раздаётся фронтом из `ICONS_DIR`; отсутствующая иконка — заглушка. Так в репозитории нет чужих картинок, а всё, кроме внешнего вида, работает без них.

**Фронт — серверный рендеринг Next.js поверх REST, без отдельного BFF.** Страницы — серверные компоненты, которые ходят в gateway; изменение данных (синхронизация) — server action. Так API не выставляется в браузер, а фронту не нужны библиотеки запросов и состояния. Графики — SVG без библиотек, по тому же принципу минимума зависимостей.

**Раннер задач на Go (`tools/dev`) вместо make/Taskfile**: на Windows нет make, а так одна и та же команда работает локально, в хуке и в CI. Версии инструментов закреплены в `tools/dev/main.go` и ставятся в `.tools/bin` (в git не попадает).

## Схема БД

Определена в `internal/db/migrations/`. Две группы таблиц:

- **Из истории матчей** (есть сразу после синхронизации): `players` (состояние синхронизации), `matches` (заголовок + очередь метаданных: `meta_status`, `meta_attempts`, `meta_next_try`, `meta_raw`), `player_matches` (строка отслеживаемого игрока).
- **Производные от метаданных** (все 12 игроков матча, пересоздаются в `StoreMeta`/`RederiveMeta`): `match_players`, `player_stats` (срезы по времени), `item_events`, `deaths`, а также колонки `matches.badge_team0/1` (средний бейдж команды) и `matches.derive_version`.

- **Профили Steam** (`RunProfiles`): `steam_profiles` — имя, ссылка, аватары, страна всех встреченных аккаунтов; `found = false` запоминает «у API профиля нет», чтобы не спрашивать снова до следующего обновления; пропавший из API профиль сохраняет последнее известное имя. `steam_friends` — друзья Steam только отслеживаемых игроков (отмечают настоящих друзей среди союзников, `Peer.steam_friend`).

Жизненный цикл `meta_status`: `pending` → `ok` | `expired` (реплей удалён, повторять бессмысленно) | `failed` (исчерпаны попытки; между попытками экспоненциальная пауза от 5 минут).

Идентификаторы `uint32` из игры (`account_id`, `item_id`) хранятся как `bigint`: в `integer` Postgres они не помещаются.

## API

Контракт — `proto/api/deadlock/v1/stats.proto`; REST-маршруты заданы аннотациями `google.api.http`, OpenAPI генерируется в `gen/openapi/api.swagger.json`, из него — TS-типы фронта `web/src/api/schema.gen.ts`.

- `account_id` в запросах — `uint64` и принимает как account id, так и SteamID64 (нормализуется в `server`); в ответах — всегда 32-битный account id.
- `ListPlayerHeroStats` — суммы по героям из истории матчей (метаданные не нужны); средние считает клиент.
- `ListPlayerMatchFacts` (`GET /v1/players/{account_id}/facts`) — сводка каждого матча игрока, от старых к новым; моменты и пороги выборки — в самом ответе (`soul_marks_s`, `soul_targets`). Души к моменту — линейная интерполяция между срезами статистики (каждые 3 мин), кривая начинается с (0, 0). `lobby_badge` — средний бейдж команд в линейной шкале рангов (см. problems.md).
- `ListPlayerPeers` (`GET /v1/players/{account_id}/peers`) — люди и герои из матчей с метаданными: союзники и соперники, встреченные `peer_min_matches`+ раз, все герои рядом и против, матчи по числу друзей в команде (друг — союзник с `friend_min_matches`+ общих матчей). Победы везде — победы запрошенного игрока. Агрегирует сервер: составы ~700 матчей — это ~8 тыс. строк, а нужны только суммы. Составы берутся из `match_players`, поэтому работает и для неотслеживаемого игрока.
- `ListSeenMatches` (`GET /v1/players/{account_id}/seen`) — строка игрока в каждом сохранённом матче с метаданными, от старых к новым; из `match_players`, поэтому работает для любого встреченного игрока. На нём профиль неотслеживаемого игрока и сравнение (`web/src/lib/seen.ts`); «я» в сравнении — первый аккаунт `SYNC_ACCOUNTS` (`web/src/lib/tracked.ts`).
- `ListProfiles` (`GET /v1/profiles?account_ids=1&account_ids=2`) — профили Steam пачкой, до 1000 id; аккаунты без профиля просто отсутствуют в ответе. Фронт считает имена украшением: при любой ошибке показывает «Игрок {id}», а не страницу ошибки.
- `ResolveSteamVanity` (`GET /v1/steam/vanity/{vanity}`) — account id по нику из ссылки `steamcommunity.com/id/<vanity>`: `NotFound` — такого профиля нет, `Unavailable` — Steam не ответил. Остальные формы ввода (SteamID64, `/profiles/<id>`, SteamID2/3) фронт разбирает сам (`web/src/lib/playerRef.ts`), без запросов.
- `ListPlayerMatches`: фильтры (`hero_id`, `result`, `game_mode`, `queue`, `meta_status`). `queue` (`MatchQueue`) — режим, как его называют игроки: рейтинг у Valve — это `match_mode` обычного `game_mode`, поэтому фильтр по `game_mode` смешивает рейтинг с обычными. Правило — `db.queueOf` (SQL) и `web/src/lib/queue.ts`, держать одинаковыми, сортировка (`sort` — дата, длительность, K/D/A, души, добивания, уровень; `ascending`) и `total` — число строк под фильтрами. Пагинация — keyset по паре (значение сортировки, `match_id`); `page_token` — непрозрачная строка `<значение>_<match_id>`, действует только с той сортировкой, с которой выдан. SQL собирается из констант (`matchSortExprs`), значения — только параметрами. Размер страницы по умолчанию 50, максимум 200.
- Ошибочные значения запроса (неизвестный enum, битый токен) — `InvalidArgument`, а не `Internal` (`db.ErrBadQuery`).
- Ошибки: `InvalidArgument` (нет обязательного id, битый токен), `NotFound`, `Unavailable` (не ответил провайдер при синхронизации), `Internal`. Текст внутренних ошибок клиенту не отдаётся (подменяется в интерцепторе), подробности — в логе.
- Аутентификации нет: порты в `docker-compose.yml` привязаны к `127.0.0.1`.

Менять API обратно-совместимо: не переиспользовать и не менять номера полей, удалённые — помечать `reserved`. Ломающие изменения — новый пакет `deadlock.v2`.
