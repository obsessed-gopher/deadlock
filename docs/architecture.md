# Архитектура

## Поток данных

```
deadlock-api.com ──(история матчей, соли URL)──┐
                                               ▼
replay<N>.valve.net ──(.meta, zstd)──► syncer ──► Postgres ◄── server (gRPC :9090) ◄── gateway (REST :8080)
```

1. `SyncPlayer` (RPC или периодический тикер по `SYNC_ACCOUNTS`) тянет историю матчей игрока и кладёт заголовки в `matches` + `player_matches`. Новые матчи получают `meta_status = 'pending'`.
2. Фоновый воркер `Syncer.Run` разбирает очередь `pending`: получает соль матча, качает `.meta` с CDN Valve, распаковывает, декодирует protobuf и в одной транзакции сохраняет сырой файл и производные таблицы.
3. API только читает из Postgres. Статические данные игры (герои, предметы) встроены в бинарник.
4. Веб-интерфейс (`web/`, Next.js) рендерит страницы на сервере, запрашивая REST-gateway; браузер с Go API напрямую не общается.

Один процесс `cmd/server` держит gRPC-сервер, REST-gateway (ходит в gRPC по loopback) и воркеры синхронизации.

## Правила зависимостей

Проверяются линтером `depguard` (`.golangci.yml`), нарушение ломает `dev check`:

- **pgx и SQL — только в `internal/db`.** Остальным нужен интерфейс, а не пул.
- **gRPC и типы API (`gen/go`) не проникают в ядро**: `meta`, `compress`, `gamedata`, `source`, `syncer` о транспорте не знают.
- **`internal/server` импортирует только `cmd/server`.**

Не проверяются автоматически, но обязательны:

- **Интерфейсы объявляет потребитель.** `server.Store`, `server.PlayerSyncer`, `syncer.Store` описывают ровно то, что нужно пакету; `*db.DB` реализует их неявно. Новый метод БД для сервера → добавить в `db` и в `server.Store`. Благодаря этому `server` и `syncer` тестируются фейками без Postgres.
- **Сборка зависимостей — только в `cmd/`.** Пакеты `internal/` не читают env и не создают друг друга.
- **Зависимости направлены вниз**: `cmd` → `server`/`syncer` → `db`/`source`/`meta` → `pb`/`compress`. Циклов и обратных импортов нет.

## Принятые решения

**`internal/db` возвращает типы API (`v1.Player`, `v1.Match`, …), а не собственные модели.** Сознательное упрощение: API сейчас — почти прямая проекция таблиц, отдельный доменный слой удвоил бы объём кода (структуры по 20+ полей и маппинг) без пользы. Цена: изменение формы ответа API затрагивает SQL-слой. Пересмотреть, когда появится логика, которой нужны данные не в форме API (агрегаты, сравнения игроков), — тогда ввести доменные типы в `db` и маппинг в `server`.

**Сырой `.meta` хранится в БД (`matches.meta_raw`).** Valve удаляет реплеи через некоторое время. `StoreMeta` идемпотентен: удаляет и заново строит производные таблицы матча, поэтому при изменении схемы данные можно пересчитать из `meta_raw` без сети.

**Провайдеры за интерфейсами.** Соль URL и историю матчей мы пока не умеем получать сами (нужен клиент Steam GC), поэтому `deadlock-api.com` спрятан за `source.SaltProvider` / `source.HistoryProvider` и заменяем.

**Собственный раннер миграций** (`db.Migrate`): файлы `NNNN_name.sql`, каждая в своей транзакции, advisory lock от гонок при одновременном старте, применяются при старте сервера. Только вперёд, без down-миграций.

**Ручной SQL, без ORM и билдеров.** Массовая вставка — через `CopyFrom`.

**Минимум зависимостей.** В `go.mod` только pgx, grpc, grpc-gateway, protobuf. zstd скопирован из stdlib; VPK, KV3 и ресурсы Source 2 разбираются собственным кодом.

**Снимок данных игры встроен в бинарник** (`go:embed`), серверу не нужна установленная игра. `item_id` в метаданных матча — это `MurmurHash2(lower(ключ), 0x31415926)`.

**Фронт — серверный рендеринг Next.js поверх REST, без отдельного BFF.** Страницы — серверные компоненты, которые ходят в gateway; изменение данных (синхронизация) — server action. Так API не выставляется в браузер, а фронту не нужны библиотеки запросов и состояния. Графики — SVG без библиотек, по тому же принципу минимума зависимостей.

**Раннер задач на Go (`tools/dev`) вместо make/Taskfile**: на Windows нет make, а так одна и та же команда работает локально, в хуке и в CI. Версии инструментов закреплены в `tools/dev/main.go` и ставятся в `.tools/bin` (в git не попадает).

## Схема БД

Определена в `internal/db/migrations/`. Две группы таблиц:

- **Из истории матчей** (есть сразу после синхронизации): `players` (состояние синхронизации), `matches` (заголовок + очередь метаданных: `meta_status`, `meta_attempts`, `meta_next_try`, `meta_raw`), `player_matches` (строка отслеживаемого игрока).
- **Производные от метаданных** (все 12 игроков матча, пересоздаются в `StoreMeta`): `match_players`, `player_stats` (срезы по времени), `item_events`, `deaths`.

Жизненный цикл `meta_status`: `pending` → `ok` | `expired` (реплей удалён, повторять бессмысленно) | `failed` (исчерпаны попытки; между попытками экспоненциальная пауза от 5 минут).

Идентификаторы `uint32` из игры (`account_id`, `item_id`) хранятся как `bigint`: в `integer` Postgres они не помещаются.

## API

Контракт — `proto/api/deadlock/v1/stats.proto`; REST-маршруты заданы аннотациями `google.api.http`, OpenAPI генерируется в `gen/openapi/api.swagger.json`, из него — TS-типы фронта `web/src/api/schema.gen.ts`.

- `account_id` в запросах — `uint64` и принимает как account id, так и SteamID64 (нормализуется в `server`); в ответах — всегда 32-битный account id.
- `ListPlayerHeroStats` — суммы по героям из истории матчей (метаданные не нужны); средние считает клиент.
- Пагинация `ListPlayerMatches` — keyset по `match_id` по убыванию; `page_token` — это `match_id` последней строки. Размер страницы по умолчанию 50, максимум 200.
- Ошибки: `InvalidArgument` (нет обязательного id, битый токен), `NotFound`, `Unavailable` (не ответил провайдер при синхронизации), `Internal`. Текст внутренних ошибок клиенту не отдаётся (подменяется в интерцепторе), подробности — в логе.
- Аутентификации нет: порты в `docker-compose.yml` привязаны к `127.0.0.1`.

Менять API обратно-совместимо: не переиспользовать и не менять номера полей, удалённые — помечать `reserved`. Ломающие изменения — новый пакет `deadlock.v2`.
